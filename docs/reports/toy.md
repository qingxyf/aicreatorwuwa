# Bilibili Toy AI 二创活动平台开发总结报告

> 报告日期：2026 年 8 月 27 日  
> 项目名称：鸣潮 AI 二创主题征集活动平台  
> 联合举办：鸣潮小站 × AI 创作小站  
> 项目性质：Bilibili Toy 小站活动，非鸣潮官方活动

## 一、项目概述

本项目旨在通过 Bilibili Toy 搭建一套完整的 AI 二创征集与投票平台，将原有活动策划中的作品投稿、人工审核、盲选和公开投票流程集中到一个网页内完成。

项目由 AI 辅助完成需求整理、界面设计、前后端开发、数据库设计、媒体存储、云服务器部署、测试、版本管理和 Toy 发布；活动主办方负责提供策划资料、视觉素材、Bilibili 账号、阿里云服务器、OSS、域名及运营规则。

## 二、需求整理与演变

项目最初依据两份活动公告进行设计，后续经过多轮沟通逐步明确为以下规则：

- 两场活动合并到同一个 Toy 页面中。
- 活动共设置四个独立赛道：
  1. 共鸣小剧场｜最佳画风奖
  2. 共鸣小剧场｜最佳剧情奖
  3. 衣锦还裳｜最佳服装设计奖
  4. 衣锦还裳｜最佳走秀视频奖
- 每个账号每个赛道最多投稿 1 件作品。
- 活动包含投稿、盲选、公开投票三个可交互阶段，以及结果公示时间节点。当前默认时间（北京时间）为：投稿 9 月 1 日–10 月 8 日、盲选 10 月 9 日–10 月 12 日、公开投票 10 月 13 日–10 月 18 日、结果公示 10 月 19 日–10 月 21 日。
- 测试期间可以同时展示三个可交互阶段和结果公示节点；正式活动时只显示当前阶段，并由服务端同时校验阶段和时间窗口。
- 用户公开页面只展示活动规则、投稿和投票，不展示运营后台入口。
- 投稿必须先经过后台审核，审核通过后才能进入盲选或公开展示。

## 三、活动业务流程

```text
B站用户进入 Toy
        ↓
Toy SDK 获取当前用户昵称、头像和 toyOpenId
        ↓
用户选择赛道并填写作品资料
        ↓
上传图片或视频
        ↓
媒体保存至阿里云 OSS，投稿资料写入 PostgreSQL
        ↓
作品进入 pending 待审核状态
        ↓
运营后台审核作品
        ↓
通过审核的作品进入盲选池
        ↓
盲选产生入围作品
        ↓
公开展示作者、头像、作品和票数
        ↓
用户参加最终投票
```

## 四、已实现功能

### 4.1 活动前端

- 单页活动首页。
- 活动标题、联合举办信息和非官方活动声明。
- 投稿、盲选、公开投票、结果公示四段时间轴。
- 四个赛道的切换和规则展示。
- 完整活动规则、免责声明、反刷票及禁止攻击服务条款。
- 投稿、盲选、最终投票和奖励区域。
- 桌面端与移动端响应式布局。
- 页面滚动入场、卡片悬浮、投票反馈等轻量动画。
- 使用活动背景图和两名角色形象作为视觉素材。

### 4.2 作品投稿

- 投稿时必须明确选择赛道。
- 根据赛道自动限制图片或视频类型。
- 图片支持分多次添加，不会覆盖此前选择的文件。
- 已选图片显示缩略图、文件名和大小。
- 支持通过缩略图右上角按钮单独删除文件。
- 自动避免同一文件被重复添加。
- 视频赛道限制为单个视频，并校验视频时长。
- 投稿成功后显示明确提示。
- 每个账号每个赛道最多提交 1 件作品。
- 投稿默认进入待审核状态，不会直接公开。

### 4.3 盲选机制

- 每个账号在每个赛道拥有 3 次盲选机会。
- 每次从两件作品中选择一件更喜欢的作品。
- 由服务器生成一次性配对任务，浏览器不能自行指定任意作品组合。
- 配对时优先选择曝光次数较少的作品，使作品总体曝光尽量均衡。
- 服务器记录作品曝光次数和盲选得票。

### 4.4 最终投票

- 展示入围作品、作者昵称、作者头像和当前票数。
- 每个账号每个赛道每天拥有 3 票。
- 同一账号当天不能重复投给同一作品。
- 票数和剩余投票次数由服务器记录和校验。

### 4.5 运营后台

- 运营后台与公开活动页面分离。
- 公开页面不展示后台入口。
- 后台使用独立密码会话保护。
- 运营人员可查看：
  - 投稿作品
  - 作者昵称与头像
  - 投稿赛道
  - 图片或视频
  - 审核状态
  - 盲选曝光与得票
  - 最终阶段票数
- 运营人员可以设置作品是否进入盲选、是否入围及是否公开展示。
- 可以配置当前活动阶段、四段时间和测试预览模式。

## 五、技术架构

| 模块 | 使用方案 | 主要职责 |
|---|---|---|
| 前端 | React、TypeScript、Vite、Ant Design | 活动页面、投稿、投票和运营界面 |
| B站接入 | Bilibili Toy JS SDK | 获取当前 Toy 内用户昵称、头像和 toyOpenId |
| 后端 | Node.js、Hono | 投稿、媒体、审核、盲选、投票和后台接口 |
| 数据库 | PostgreSQL | 用户、投稿、媒体元数据、配对、票数和活动配置 |
| 媒体存储 | 阿里云 OSS | 保存用户上传的图片和视频 |
| 服务器 | 阿里云 ECS、Docker Compose | 部署 API 和 PostgreSQL |
| HTTPS | 已备案二级域名 | 连接 Toy HTTPS 前端与 ECS 后端 |
| 代码托管 | GitHub | 保存源码、版本记录和静态预览 |
| 正式前端托管 | Bilibili Toy | 承载活动静态页面并提供访问入口 |

## 六、数据存放方式

### PostgreSQL 保存的数据

- 活动阶段与时间设置。
- Toy 用户开放标识、昵称和头像。
- 投稿标题、说明、角色名称和所属赛道。
- 媒体文件元数据及归属关系。
- 投稿审核、入围和展示状态。
- 盲选配对任务、曝光次数和盲选票。
- 最终投票记录和票数。
- 运营会话及接口限流数据。

### 阿里云 OSS 保存的数据

- 用户投稿图片。
- 用户投稿视频。

OSS Bucket 按项目要求保持公共读、私有写，但活动上传对象使用对象级私有权限；未审核媒体通过受控接口或短时签名地址提供给运营后台查看，避免待审核内容直接公开。

## 七、基础安全措施

项目目前实现的基础防护包括：

- PostgreSQL 查询使用参数化语句，降低 SQL 注入风险。
- 服务端不信任浏览器提交的作品状态、票数或赛道限制。
- 服务端校验投稿阶段、文件归属、投稿数量和投票次数。
- 校验文件 MIME、文件大小及二进制文件签名。
- 限制 JSON 请求体和媒体文件大小。
- 对写接口进行按账号和路由限流。
- 盲选使用服务器签发的一次性配对任务。
- 运营后台使用独立密码和短时会话令牌。
- 待审核媒体不会通过公开活动接口直接返回。

需要特别说明：Toy SDK 返回的 `toyOpenId` 是当前 Toy 内的稳定开放标识，但不是服务端可验证的登录凭证。当前内部测试模式允许使用该信息作为弱身份，因此能够满足投稿和投票测试，但不能完全阻止恶意请求者伪造身份。正式大规模公开活动前，仍建议接入平台提供的可验证身份方案或增加更严格的服务端风控。

## 八、部署与发布方式

- 前端源码保存于 GitHub 仓库。
- GitHub Pages 提供静态页面预览。
- 正式活动前端通过 Toy CLI 构建并上传到 Bilibili Toy。
- Toy 更新采用“生成预览 → 人工检查 → 明确确认 → 提交审核”的流程。
- Toy 静态包采用相对资源路径，适配 `/toy/aicreatorwuwa/` 子路径。
- 当前使用密码访问模式进行内部测试，之后可以切换为公开访问模式。
- 后端和 PostgreSQL 运行在阿里云 ECS 上，媒体文件保存到阿里云 OSS。

## 十、问题排查与关键修复

开发过程中主要处理了以下问题：

- 修复 Toy 子路径下资源加载和旧版本缓存问题。
- 修复普通 `fetch` 调用导致的 `Illegal invocation`。
- 修复 Toy SDK 尚未完成宿主握手时出现的 `toy id not available on host`。
- 修复上传后无法在后台查看媒体的问题。
- 修复公共读 Bucket 下待审核对象可能被直接访问的问题。
- 修复活动阶段、四赛道和服务端时间窗口不一致的问题。
- 修复盲选曝光统计和展廊 PostgreSQL 查询问题。
- 增加同账号同赛道唯一投稿约束。
- 将图片选择从一次性覆盖改为可多次追加、预览和删除。

## 十一、当前完成度

目前已经跑通以下完整链路：

```text
进入 Bilibili Toy
→ 获取 Toy 用户资料
→ 选择赛道投稿
→ 图片或视频上传至 OSS
→ 投稿数据写入 PostgreSQL
→ 后台审核作品
→ 进入盲选
→ 设置入围作品
→ 公开展示和最终投票
→ 保存并展示票数
```

因此，项目已经具备内部测试和活动演练所需的主要功能。

## 十二、后续工作建议

正式活动开放前还需要完成以下运营和验证工作：

1. 如需调整正式活动时间，由运营后台统一修改投稿（9 月 1 日–10 月 8 日）、盲选（10 月 9 日–10 月 12 日）、公开投票（10 月 13 日–10 月 18 日）和结果公示（10 月 19 日–10 月 21 日）四段时间，并保存后复核公开页时间轴。
2. 确定各赛道入围数量及晋级规则。
3. 补充奖品名称、数量、发放方式和获奖公示规则。
4. 使用多个真实 B站账号完成投稿、审核、盲选和投票全流程测试。
5. 根据预计并发量进行一次有限压力测试。
6. 复核 ECS 安全组、反向代理、日志、备份和 OSS 生命周期规则。
7. 正式活动前关闭测试预览模式，并将 Toy 从密码访问切换到公开访问。
8. 如果活动规模扩大，补充更强的身份校验和异常投票风控。

## 十三、总结

本项目已经从两份活动策划公告发展为一套可运行的 Bilibili Toy 投稿与投票平台。AI 不仅用于生成页面，也参与了需求分析、技术架构、前后端实现、数据库、云端部署、安全检查、测试和发布排错。

目前系统已完成“用户投稿—云端存储—运营审核—盲选—入围—公开投票”的主要闭环，可以作为 Bilibili Toy 活动的一种新玩法继续进行内部测试和正式活动准备。
