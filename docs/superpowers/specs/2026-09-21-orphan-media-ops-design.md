# 孤立媒体运营可见性与投稿媒体浏览设计

## 背景

生产数据库中有 5 条投稿、46 条媒体记录，其中只有 23 条媒体被投稿的 `media_json` 引用，另外 23 条媒体已经上传但没有投稿记录。当前运营接口只查询 `submissions`，因此这些媒体不会出现在后台。媒体上传先于投稿创建，提交失败、页面中断或重复投稿都会留下这种记录。

## 目标

- 保留历史孤立媒体，并让运营后台能按上传人和上传批次查看。
- 展示可确认的上传人 ID、时间、媒体数量和“未生成投稿记录”原因；历史数据无法推断的标题、赛道和昵称不猜测。
- 后台正常投稿和孤立媒体都支持点击缩略图，查看该作品/批次的全部大图或视频。
- 新上传流程记录批次、投稿资料和失败原因，便于以后准确追踪。
- 不自动删除媒体，不把缺少必要投稿资料的孤立媒体伪造成正式投稿。

## 方案

`submission_attempts` 保存一次投稿尝试的稳定 ID、用户身份、赛道、标题、说明、状态和失败原因；`media_objects.attempt_id` 把上传媒体关联到尝试。客户端在上传前生成尝试 ID，并把已填写的投稿资料随每个媒体上传发送。投稿成功后将尝试标记为 `submitted`；投稿接口校验失败时标记为 `failed`；页面在上传后中断的尝试保持 `uploading`。

运营端新增受保护的孤立媒体查询。带尝试 ID 的媒体按尝试分组；历史媒体按用户 ID 与十分钟时间窗口分组，并标注为历史数据、具体失败原因不可追溯。接口为每个媒体签发短时运营访问地址。

后台保留正常投稿表格，增加孤立媒体区域和孤立媒体数量统计。媒体预览使用一个通用浏览器弹窗，支持图片、视频、上一张、下一张、缩略图跳转和键盘可访问操作。

## 数据安全

- 所有孤立查询仅对已通过运营密码会话的请求开放。
- 不删除 OSS 对象或数据库媒体记录。
- 历史孤立记录只展示数据库中存在的稳定用户 ID；没有可靠的昵称/赛道时显示未知，不调用猜测逻辑。
- 正常投稿的公开展示和投票接口保持不变。

## 验证

- 迁移与 repository 查询测试覆盖孤立媒体、尝试状态和历史分组。
- API 测试覆盖运营鉴权、签名媒体 URL 和投稿失败标记。
- React 测试覆盖孤立媒体展示、统计数量和点击后浏览全部媒体。
- 运行完整 Vitest、TypeScript 构建和 ESLint。
